状态：实施中，PR01 [#9](https://github.com/LoTwT/puzzle/pull/9)、PR02 [#10](https://github.com/LoTwT/puzzle/pull/10)、PR03 [#11](https://github.com/LoTwT/puzzle/pull/11)、PR04 [#12](https://github.com/LoTwT/puzzle/pull/12) 已合并，GitHub CI 与 Cloudflare Pages 检查通过；PR05 实施、本地验证与父协调审查通过，进入提交、推送和 PR 发布阶段，远端检查随发布确认；PR06、PR07 待实施。更新日期：2026-10-16。

将[首版规格](web-puzzle-v1.md)中已确定的内容拆成 7 个 PR，按下表顺序合入。PR01 至 PR07 是计划编号，不对应 GitHub PR 号。本文维护任务归属、依赖和验证安排；玩法、参数、数据模型与最终工程要求仍以首版规格为准。

工程基础从只有项目指导和规格文档的仓库开始。整个实现会新增超过 8 个文件，其中 PR01 的工程配置最多；仍保持一个前端应用包，不新增服务、账号或密钥。拆分保持一次首版交付：PR01 提供可运行的工程基础，PR02 起每个 PR 都保留可完整游玩一局的应用，但全部首版能力及验收需由后续 PR 补齐。

## 共用合入要求

- 每个 PR 包含本范围的实现与验证，已有可用流程持续通过检查；生产页面只展示该 PR 已接通的操作入口。
- 检查脚本随可执行内容接入。PR01 的 CI 执行格式、lint、类型检查和构建；PR02 增加规则测试后，`pnpm run ci` 达到规格规定的完整顺序。PR04 增加浏览器测试命令。
- 常规 CI 始终保持一个 Ubuntu job，不安装浏览器。PR04 起，涉及输入、图片、存档或动画的变更按需运行 Chromium 关键流程；PR07 执行全部三个浏览器项目及实际设备验收。
- 实现时选定并锁定规格指定发布线的具体工具版本。新增脚本、配置与操作说明同步维护在 `docs/development.md`，README 和文档索引提供入口。
- 当前规格中的文件职责保持不变。共享类型按首次使用的 PR 引入；规则负责计算，会话负责提交，动画负责视觉收尾，存储模块只返回恢复快照或接收保存请求。模块关系见[实现方案与文件边界](web-puzzle-v1.md#实现方案与文件边界)。
- 每项 PR 由新的独立 Astra session 实施与验证，父协调 session 审查并要求必要修复；通过后按具体指令提交、推送、创建 PR 和合并，再推进下一项。
- 过程中维持规格的基本界面质量。视觉反馈与实际手机验收留到最后统一进行，不阻塞此前 PR 的实施和合并；模拟验证与真机结果分别记录，未做的验收保持未验证。

## 实施时的边界

主要风险集中在图片异步任务、交换提交、存档写入和动画回调之间的先后顺序。各 PR 以同一个会话标识和交换提交入口衔接，过期任务不得改变当前局面；图片失败、存储失败和动画取消分别按规格处理。

用户已授权从拆分进入实施阶段，原先仅产出文档的范围约束已被覆盖。PR01 至 PR04 已合并且远端检查通过；PR05 已通过实施、本地验证与父协调审查，当前进入提交、推送和 PR 发布阶段，远端检查通过后由父协调核对、合并与清理。后续各项仍按独立 session 实施、父协调审查、发布与合并的顺序推进。上线部署不在本流程内。

实施后如需回退，按依赖逆序处理；涉及存档的回退保持数据库记录，不以清空浏览器数据代替兼容处理。首版存档格式已在规格中确定，格式变更须另行设计兼容策略。
